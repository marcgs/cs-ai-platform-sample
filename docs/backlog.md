# Backlog

Every idea for the platform in one place: findings from running it, scope the [specification](specification.md) defers, and new directions. Items are grouped by theme and have a stable ID (`B3`), so iteration plans can refer to them.

## How to use it

- **Add an idea** to the theme it fits, with the next free ID. IDs are never reused or renumbered.
- **Size** is a rough first guess: **S** up to a day, **M** a few days, **L** a week or more.
- **Target** is empty until an iteration takes the item; then it names the iteration (`it2`). When an item is done, write `done it2` and link the pull request in the notes.
- An iteration's scope and order live in its plan (`docs/plan-iteration-N.md`), which lists the IDs it takes.

## B. Controlled learning

The idea: make **skills** the unit the platform versions, evaluates and improves, and let a learner propose changes that only an expert and the eval gate can release. Two candidate learners: [Hermes Agent](https://hermes-agent.nousresearch.com/docs) (open source), a harness with a built-in learning loop that writes and refines its own skills in the open agentskills.io format (B4); and a coding agent hillclimbing against the eval (B7).

| ID | Item | Why | Notes | Size | Target |
|---|---|---|---|---|---|
| B1 | **The RCA procedure as a skill** | The agent's behavior is buried in `instructions.md`. A skill is a versioned, reviewable artifact, and the unit the learning loop changes. It's also what C1 runs on another harness. | Move the investigation procedure and answer rules to `skills/rca-investigation/` (`SKILL.md`, plus a script only if one earns its place). `rca-agent` loads it with no change in behavior; the eval baseline proves it. Check how Agent Framework loads skills. Foundry has its own skills (preview): versioned skills in the project, loaded by the agent at startup or attached to a toolbox, and a private skill catalog in Azure API Center with allowed tools per skill (H8). | S | |
| B2 | **Episodes and feedback as MCP tools** | Gives a learner agent governed, read-only access to what experts said. | Read-only MCP tools on the platform API (list episodes by verdict, get episode), behind the same identity and network rules. | S | |
| B3 | **Proposals, replay and approval** | The specification's controlled loop: no change to agent behavior without expert approval and a passing replay. | A proposal is a skill change plus new eval cases that reproduce the mistakes it fixes. `csai eval` replays it against those cases and the full suite, and must fix them without regressions. Replay uses the keep/revert rule from G8: keep only when both the train and the held-out cases improve beyond the measured noise. An expert approves (`csai proposals approve`, or a pull request review), and `azd deploy` releases it as a new agent version linked to the proposal. | M | |
| B4 | **Hermes as the learner** | Hermes's self-improvement is what the loop needs, but uncontrolled; behind the gate (B3), it only proposes. | A hosted container (bring-your-own-framework path) on Foundry models, using the B2 tools to draft proposals from episodes marked incorrect. Its Foundry guide covers Foundry as a model provider, not as a hosted agent: verify that first. Needs a supply-chain review as a third-party dependency, and an image built in Azure. First target: D1. | M | |
| B5 | **Confirmed cases become knowledge** | Every expert-confirmed diagnosis is a new historical case; today the index only holds seed data. | Turn episodes with a confirmed root cause into `diagnostics-cases` documents, as a proposal an expert approves (B3). | S | |
| B6 | **Scheduled review and an approval flow** | The specification's periodic review of episodes, with approvals outside a terminal. | Run the learner on a schedule, or on new feedback through the Cosmos DB change feed and a function; approvals through Logic Apps or the review app (F1). | M | |
| B7 | **Hillclimbing with Claude Code as the learner** | A second way to draft proposals, next to Hermes (B4): a coding agent improves the agent against the eval one change at a time, and keeps only changes that hold up on held-out cases. Running both learners on the same failures shows which kind suits the loop. | Follow [Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/): each round reads the train failures, proposes one patch to a cheap, attributable surface (the B1 skill, tool descriptions, model or effort), and applies G8's keep/revert rule. When the score stalls, sort the remaining failures by cause before more rounds; they're often broken cases. Never paste failures into the skill. Claude Code's `/claude-api build-eval` and `/claude-api hillclimb` workflows target apps on the Claude API, so check whether they can drive `csai eval` for this agent, or follow the method by hand. The result is a B3 proposal, not a merge. | M | |
| B8 | **Foundry's agent optimizer as the learner** | A managed learner built into Foundry: it evaluates a hosted agent against a dataset and generates better instructions, skills, tool descriptions or model choices. A third learner to compare with B4 and B7, and the one closest to the platform. | [Agent optimizer](https://learn.microsoft.com/azure/foundry/agents/concepts/agent-optimizer-overview) (preview): make the agent "optimizer-ready" (it loads its configuration through the optimizer package), pick an evaluation model and an optimization model (gpt-5 family or DeepSeek), and run it with the `azure.ai.agents` azd extension. Feed it the G8 train cases and check its candidate against the held-out ones with `csai eval` before it becomes a B3 proposal. Datasets can also be built from agent traces. | M | |
| B9 | **Fine-tuning from confirmed episodes** | Learning through model weights instead of skills: a smaller model trained on expert-confirmed diagnoses could match a larger one at lower cost. | Reinforcement fine-tuning with graders (string check, model or Python graders), where our code evaluators become the reward. Check which models and regions support it. Stored-completions distillation retired on 2026-10-15, so build the training set from episodes. Keep train, validation and test cases apart (G8). Compare the result with G9. | L | |

## G. Measuring quality

A good eval mirrors real use, scores higher for more capable models, leaves headroom, and has low run-to-run variance ([Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)). Today's suite is saturated: every case passes at baseline.

| ID | Item | Why | Notes | Size | Target |
|---|---|---|---|---|---|
| G1 | **Harder eval cases** | 18 synthetic cases, all solved at baseline: the suite checks regressions, not headroom. | Source cases from real use first: episodes experts marked incorrect or partially correct, then hand-written cases, then synthetic ones anchored in them. Cover ambiguous symptoms, misleading logbook entries, unknown machines, injected instructions, multi-turn follow-ups. Each case should be hard for a reason an expert can explain, not just one today's model happens to fail. Add per-failure-mode breakdowns. | M | |
| G2 | **Model-graded judges, locally** | The specification asks for model-based evaluators; there are none yet. | Groundedness, task adherence and intent resolution from `azure-ai-evaluation`, run by the harness next to the code evaluators. Prefer rubrics of checkable claims to 1–5 scales; compare against a baseline blind, in random order; use a judge model other than the one under test. Check a sample of verdicts by hand before trusting the judge. | S | |
| G3 | **Evaluations published to Foundry** | `csai eval --publish` fails in a network-injected project: cloud evaluations need account- and project-level capability hosts (and evaluation storage). | Capability hosts must be set when the project is created: plan a rebuild, or a separate evaluation project. G2 covers the judges in the meantime. | M | |
| G4 | **Red-teaming** | Prompt injection through tool data and user input is a real risk for a diagnostics agent. | Foundry's AI red-teaming agent against `rca-agent`; findings become eval cases (G1). | M | |
| G5 | **Cost and latency per diagnosis** | "Time to diagnosis" is the specification's main outcome, and cost decides which model to use. | Record tokens, cost and duration per episode and per eval case; report them in `csai eval`. | S | |
| G6 | **Model comparison** | The model is configuration; numbers should drive the choice. | Run the suite across models and providers in the Foundry catalog (OpenAI, Mistral, DeepSeek, Claude, open models), compared on quality against cost and latency (G5). Check data-zone availability per model; a model from another provider also makes a good independent judge for G2. | M | |
| G7 | **Eval health checks** | A gate is only as good as its signal. Today nobody knows how much scores vary between runs, whether a failure was the model or the plumbing, or whether the suite still has headroom. | `csai eval` reports: run-to-run variance (repeats per case, confidence intervals), grader consistency (grade the same output twice), plumbing failures (timeouts, API errors, truncated answers) separately from wrong answers, and a warning when the baseline is near 100%. Write one transcript per case next to `results.jsonl`, and a static results page. | S | |
| G8 | **Train and held-out cases** | Without held-out cases, a change that fits the cases it was tuned on looks like an improvement. B3 and B7 need this to tell real gains from overfitting. | Mark each case `train` or `test` in `cases.jsonl` (random split, fixed seed). Keep/revert rule: keep a change only when train and test both improve by more than the measured noise (G7); train up and test flat means overfitting, so revert. Learners never see test transcripts. | S | |
| G9 | **Cost at equal quality** | When an eval saturates, the useful goal is the same quality for less. The blog's example cut cost to a fifth while held-out accuracy went up. | Hillclimb (B7) on model, effort and an audit of the instructions for steps that cost tokens without helping, with quality held at the thresholds. Needs G5 for cost, G8 for the held-out check. | M | |
| G10 | **Review what the metrics reward** | `tool_coverage` rewards calling every diagnostic tool, which is a ritual, not an outcome. It would penalize a cheaper agent that skips a tool it doesn't need (G9). | Decide per metric whether it measures the outcome (right root cause, grounded evidence) or a process; keep process metrics as diagnostics rather than gates. Revisit thresholds after G1. | S | |
| G11 | **Model router** | Foundry picks a model per request from a pool (cheap models for easy prompts, stronger ones for hard ones), which may give G9's savings with no tuning. | [Model router](https://learn.microsoft.com/azure/foundry/openai/concepts/model-router): one deployment, Balanced, Cost or Quality mode, and an optional model subset; works for agents with tools and honors data-zone boundaries. Each response names the model that served it, so record it in the episode. Run the suite against it next to the direct deployment: does quality hold, and what does it cost? | S | |
| G12 | **Continuous and scheduled evaluation** | `csai eval` checks fixed cases before a release. Live traffic drifts, and needs scoring too. | Foundry's [continuous evaluation](https://learn.microsoft.com/azure/foundry/observability/how-to/how-to-monitor-agents-dashboard#set-up-continuous-evaluation) samples live traffic, and scheduled evaluations rerun a dataset, both shown on the agent's monitoring dashboard. Custom evaluators can join the built-in ones. Related: datasets from traces, cluster analysis of failures, human evaluation of traces, scheduled red-teaming (G4). Check whether these cloud evaluations need the capability hosts that block G3. | M | |

## K. Production readiness

What it takes to run agents on the platform in production, beyond deploying them. Suggested order: K1, K3 and K4 tell one story (promote a version, watch it, stop or roll it back), K2 needs the most infrastructure change, and K5 fits best once the platform has settled.

| ID | Item | Why | Notes | Size | Target |
|---|---|---|---|---|---|
| K1 | **Environments, promotion and safer releases** | Every project asks how a new agent version reaches production safely, and how to undo it. | dev, test and prod as separate azd environments from the same Bicep, with per-environment parameters.
